# Castle of Illusion: early object activation for 21:9 (GAMEPLAY-CHANGING)

An opt-in variant, separate from the presentation-only package [`castle-of-illusion`](../castle-of-illusion/README.md), which it does not replace and never modifies. It shares that package's provider (`src/provider.c` is a byte-identical copy, enforced by `tests/test_castle_activation.py`) and adds, through the existing typed mechanisms only:

* **nine typed ROM edits** (`edits/activation.edits`, every site asserts its original value): the right column lookahead 0x180 -> 0x280, the left column lookahead 0x71 -> 0x100, the initial-fill bound (it runs the *left* branch of the column loader, so it moves with both lookaheads), the row-loader span, and five six-byte hook sites;
* **a bounded guest-asm routine** (`src/retry.asm`, five hooks, each an absolute jump into it and back to an original continuation) that (1) clears and arms its state at the game's single level-initialization call, before anything can use it; (2) queues, in four slots, the (column,row) of a section load whose object allocation failed (pool full) and re-runs the ORIGINAL loader for it once per streamer invocation for at most 24 invocations, only while the section is inside the camera window; (3) replaces the object window test at `0x1b12`.

It changes which layout objects exist and when (more enemies and items alive earlier and farther away, on both sides), so it is **gameplay-changing**. **The static ROM edits and hooks are part of the image: they stay active whatever the presentation settings, including Original mode and narrower aspects** (choosing a smaller widescreen ratio does not undo them; use the presentation-only package or Vanilla for that).

## What the game does (the sprite-construction trace)
The per-object draw routine (`0x1ab6`, run over a draw list) does, in this order: animation advance; **the object window test (`0x1b12`: `CMPI #$280,D4 / BCC` on D4 = screen x + 128, then `0x1b20` the same for y)**; mapping expansion; for every piece the vertical clip (`0x1c1e`, sprite y 0x60..0x17f) and the **piece x clip (`0x1c34`, sprite x 0x60..0x1df = screen -32..351)**, which silently drops a piece.
* The window test is a **deletion** (it jumps to the object free path `0x1c94`), not a presentation predicate: it decides which objects exist (AI, collisions, the section bookkeeping flag that lets the entry be created again). It is an *unsigned* compare, so **every object left of the camera was deleted** - the original never had a left activation window. The previous revision of this package hooked the following signed `TST/BMI`, which the unsigned branch had already made unreachable: left activations were created and deleted within one frame (50 of 58). The hook now sits at `0x1b12` and implements one signed window `[-(left lookahead+0x100), 0x380)`.
* The piece x clip is presentation-only (it undoes its own sprite-link counter and writes nothing else); the existing provider already observes every piece at its entry (`before` hook) and draws the dropped ones, so **no sprite-construction change is needed**: pieces of objects far outside the picture do reach that hook (a claim of the previous report, that the builder emits no pieces for distant objects, was wrong; the loss was the deletion).
* The window test must keep deleting **dead slots**: the draw list is stale at a level change and a freed slot (type word 0, x 0) was removed by the unsigned test as "left of the camera"; drawing it reads a null mapping pointer (an odd-address stop in the first attempt at the signed window, found by the attract-demo level exit). The hook therefore still deletes a slot with type 0 when it is left of the camera, and leaves the original behavior unchanged right of it.

## Supported scope
Validated only for **21:9** (the manifest claims `aspect_max = "21:9"`). The provider itself presents scenery and actors up to 32:9 (see the presentation-only package); this variant's activation is not validated for 32:9 and no 32:9 activation is offered (see Limits).

* **Determinism, rewind, quick-save.** Two straight runs of the same program (stage 4-0, active hooks) produce identical event streams (15,167 events). Treat quick-save restore inside this variant as approximately, not exactly, deterministic.
* The injected code is executed, not only read: `tests/test_castle_activation_exec.py` assembles the shipped `retry.asm` and runs it natively on a synthetic image against stubs of the original loader; 20 tests assert the continuation path taken and the stopping point, every register, the stack pointer, the **complete work RAM image** (except the retry state, the stub counters and the stack area) and the CCR (X and the flags the original would leave) for initialization, level reset with four slots occupied, enqueue, dedup, queue-full, no enqueue while retrying or with a bad key, success, failure ageing, expiry, invalidation, the window edges, the entry hook and the left deletion (dead slot, both boundaries). Mutations of the code (unsigned compare restored, flag restoration removed, an X-writing instruction added, key check after the vertical loader, a slot missed by the reset, a write outside the extent) are caught. A CI job builds the pinned product CLI and fails if the tests do not run.

## State, register and flag argument
* State: 48 bytes at `0xFFFC00..0xFFFC2F`. The original game never wrote `0xFFFC00..0xFFFC3F` in 29 stages or in a 60,000-frame run from boot (logos, title, attract demos, levels); lowest stack pointer 0xFFFEA0, about 620 bytes above the extent. The streamer (and so every hook) does not run before the first level initialization; the level initialization has a single call site, which the routine hooks to clear and arm the state first, and every hook also arms or refuses on a wrong key before first use. Soft reset keeps work RAM on hardware: a stale ring survives a reset but nothing can read it before the next level initialization clears it (the streamer and the loader run only inside a level).
* The queued section's list pointer is not stored: it is a function of the level layout and is rebuilt as the original does; the retried loader receives the same a1/a2 as the original.
* **Condition codes.** The previous text was wrong: `LEA` and `DBF` do not rewrite the CCR. The argument is now per continuation, and tested: **no hook instruction writes X** (only `MOVE`, `MOVEA`, `LEA`, `CMP`, `TST`, `CLR`, `ROR`, `ANDI`, `MOVEQ`, `DBRA`, `JMP`/`JSR` are used; a test rejects any X-writing mnemonic, and the guest assembler forbids reading or writing SR/CCR), so X is preserved at every continuation. N/Z/V/C: *entry hook* - the last instruction before the continuation is the displaced `MOVEQ #0,D3`, exactly the original's flag-setting instruction; *fail hook* - the original `DBF` leaves the CCR as the scan loop's last `TST.W` set it, and that CCR flows out through `MOVEM`/`RTS` to the caller, so the hook ends with `TST.W -$40(A3)` (the slot the scan last tested), reproducing N (sign of the slot word), Z=0, V=0, C=0; *frame hook* - the continuation (`MOVE.W 4(A6),D0`) rewrites N/Z/V/C; *level reset* - the continuation (`MOVEQ #0,D4`) rewrites them; *left deletion* - the continuations (`CMPI.W #$280,D3` and `TST.W $24(A0)`) rewrite them. The frame hook uses `ROR` + mask and `LEA`/`MOVEA` for its shifts and arithmetic precisely because `ASR/LSR/ADD/SUB` write X.
* Registers: the displaced `MOVEM` (d2,d5,d7,a2) is reproduced by four pushes in the original memory order; the frame hook preserves d0-d7/a0-a6 and sets a6 to `0xFFFFFA80` exactly as the original `LEA` did; the fail hook preserves d0/d1/a0 and leaves d6 as the original `DBF` left it; the level-reset hook and the window hook preserve every register (d4 is not modified).
* A retried section calls the original loader, which skips entries whose loaded flag is set and applies its own rules for filtered or retired entries; nothing is created that an original section reload would not have created. Across the 29 passive and 9 active stages the heuristic "an entry activated again after the object left by a path other than the off-screen deletion" occurred 0 times with the variant (2 with the original in the active runs); rewards were not inspected one by one.

## Limits (not measured or not achieved)
* **32:9 is not provided.** A 32:9 candidate (right 0x2c0, left 0x180) still lost 6 of 168 original objects (stages 4-0, 3-2) and expired 5 retries. The corrected analysis of the pool pressure: layout objects allocate in **one 32-slot range (`0xD400..0xDBFF`)**, not in a 48-slot pool (the lower 16 slots of `0xD000..0xD7FF` belong to another class); in the 50 pool-full moments of the candidate that range held a median 19 and at most 20 objects *inside the 32:9 viewport* and 13 (at most 15) outside it (speculative or already passed). Objects in the viewport never reached the 32 slots, so a physically larger pool is not needed; the failures are caused by objects outside the viewport. A policy that keeps those out of the pool (deferring speculative sections while the range is nearly full, or freeing an out-of-view object through the original free path `0x1c94` when an in-view section fails) is the next bounded experiment; relocating a pool is not (about 35 static references to the pool bases plus per-object links). Neither policy is implemented.
* Item collection, damage, collision and RNG behavior were not compared beyond object identity and kill/collect events (frame-by-frame replay of an original script does not stay bit-identical because extra per-frame work shifts timing); RNG and audio samples were not compared sample by sample.
* No boss was defeated; the arenas were entered and fought with a scripted pattern (no guest stop, comparable death/restart counts and camera progress).
* Pixel continuity was measured in one stage at 21:9 (the 16:9 package was not measured at pixel level).
* Soft reset was not forced in a running game (argued above); pending retries across a real level transition were not observed in the real game (none pending at 50 resets), only in the executable fixture.

## W04 follow-up 2 (determinism, X flag, visible sprite capacity)

**Quick-save determinism (Task A) - the guest is deterministic; no injection defect.** A private probe (not committed; product at `8d419ab` plus a local diagnostic) snapshots the whole machine (the product's canonical SGSTATE container: CPU, work RAM, VDP, devices, Z80, sound) at a guest frame boundary or at an arbitrary mid-frame dispatch barrier (+0, +37, +1500, +4001), restores it later and replays under the identical input schedule. Frame-boundary digests (full container, work RAM, PC, SR, d0-a7, camera words, master ticks) of the replay equal the straight run **for every frame (200 after a boundary snapshot, 99 for each of nine mid-frame combinations) in the original, the typed edits alone, the hook-free 16:9 package, a pass-through injection of all five hook sites, and the full 21:9 variant**. So the injection changes timing (master ticks differ between variants) but not restorability, and the earliest divergence is not in the guest. In the real viewer (21:9, stage 1, native presenter, `K` then `M` through the pad-script seam) the **native 320 px picture is bit-identical** to the uninterrupted run from the first real frame after the load; what differs for exactly **one frame** is the widescreen margin: the host shows its fallback fill with "current game state not verified" instead of the authored scenery. The pass-through 21:9 package and the hook-free 16:9 package show it equally (so it is not injection related). An instrumented provider shows frame-end and render run with a valid scene on that frame; only phases 7 and 8 run (the restore lands mid-frame, so input/post-input of that frame never run) and the host still reports the state unverified, a host-side behaviour of the first frame after a load that affects every native-provider package. **A 1 px shift of the native picture was not reproduced** here (stage 1; stage 4-0 was not re-run), so the earlier camera observation remains unexplained at stage 4-0 and no product PR was opened: no minimal synthetic fixture exists yet for the margin transient. The pad script is keyed by host poll, not guest frame, so frames after the first few of a restored run are not comparable with an uninterrupted run (input misalignment, not a defect).

**X flag (Task B).** The hook cannot save/restore X: the product assembler has no ADDX/ROXL and forbids SR access. The extra original-loader calls do change X (a synthetic loader that flips X on every call pins this in `test_the_hook_does_not_preserve_x_across_extra_loader_calls_...`). Liveness evidence, not proof: the continuation (streamer tail 0x6d53c, returning into the per-frame update at 0x9808) starts with a MOVE.W that rewrites N/Z/V/C, the statically reachable code from the return point to its RTS (221 instructions) contains no X reader, and forcing X to 0 versus 1 right before the continuation gave a bit-identical machine digest on all 3,002 frames of a scrolling run. A whole-ROM static proof is not possible (indirect dispatch). The CI executable-test step now has `set -euo pipefail`; `tests/test_ci_exec_step.py` runs the real step against failing, erroring, skipped, import-broken and passing stub suites (without pipefail the failing suite passed the step).

**Visible sprite capacity (Task C).** Hook time: a candidate no placement of any package could show is dropped before it takes a place (beyond the widest 32:9 view, or off the 224 raster rows); the rest go to a 128-entry scratch in the game's order, tagged "likely" from the host's last plan and the camera, and under pressure a likely piece evicts the newest unlikely one. Render time: the exact selection against the presented view (`[-left, 320 + 2*margin - left)` when the placement was built for this plan; the widest placement of the plan when it changed; the picture only without an extension; kept edge pieces count by the part beside the raster), at most the host's own 64 commands (was 48 by this provider), the game's order and priority layers kept. A visible loss is counted and logged once when it starts through `host.log` (now a declared capability in all three packages; without it the host disables the mod). The sampled left-scroll refusal ("virtual sprites not presented") is the case where the pieces lie left of a picture placed at the view's left edge (camera < margin): there is no presented column there, so the host correctly refuses; the provider now never submits them.

**Not done in this update:** Task D (32:9 deferral of speculative sections) and Task E (expanded pixel acceptance: 16:9, dense, red-water, leftward, bosses, item/damage/progression, final-package replay/rewind) were not started; 32:9 remains not provided, and the claims of the previous report for those tasks stand unchanged. Task C was verified by unit tests (44) and a run in the real 21:9 viewer without a mod fault, not by a new pixel campaign.

## W04 follow-up 3: deferral and queue reservation now apply to 21:9 (supersedes the retry description above where they disagree)

Besides the retry it now has the **deferral** of speculative sections (layout pool 0xD400..0xDBFF at 20 or more objects AND the section beyond the original window AND fewer than 12 ring slots in use), a **16-slot ring** and diagnostics at 0xFFFCA0.. With the deferral: **6 full-pool frames in the whole 29-stage sweep, 3 failures (all retried), 0 expired, 0 ring drops**, queue maximum 12 (the cap), maximum recovery latency 1,287 streamer invocations (a section waiting for room, not failing). On the deterministic hold-right route: 0 original identities lost (26 stages), 86 created early; pool never full.
