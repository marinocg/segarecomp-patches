# Castle of Illusion: early object activation for 21:9 (GAMEPLAY-CHANGING)

An opt-in variant, separate from the presentation-only package [`castle-of-illusion`](../castle-of-illusion/README.md), which it does not replace and never modifies. It shares that package's provider (`src/provider.c` is a byte-identical copy, enforced by `tests/test_castle_activation.py`) and adds, through the existing typed mechanisms only:

* **ten typed ROM edits** (`edits/activation.edits`, every site asserts its original value): the right column lookahead 0x180 -> 0x280, the left column lookahead 0x71 -> 0x100, the initial-fill bound (it runs the *left* branch of the column loader, so it moves with both lookaheads), the row-loader span, the right off-screen deletion limit, and five six-byte hook sites;
* **a bounded guest-asm routine** (`src/retry.asm`, 630 bytes, five hooks, each an absolute jump into it and back to the original continuation) that (1) clears and arms its state at the game's single level-initialization call, before anything can use it; (2) queues, in four slots, the (column,row) of a section load whose object allocation failed (pool full) and re-runs the ORIGINAL loader for it once per streamer invocation for at most 24 invocations, only while the section is inside the camera window; (3) moves the left off-screen deletion limit to the left lookahead (the original deleted at 128 px).

It changes which layout objects exist and when (more enemies and items alive earlier and farther away, on both sides), so it is **gameplay-changing**. **The static ROM edits and hooks are part of the image: they stay active whatever the presentation settings, including Original mode and narrower aspects** (they are not undone by choosing a smaller widescreen ratio; use the presentation-only package or Vanilla for that).

## Supported scope
Validated only for **21:9** (the manifest claims `aspect_max = "21:9"`). The provider itself presents scenery and actors up to 32:9 (see the presentation-only package), but this variant's activation is **not** validated for 32:9, and no 32:9 activation is offered (see Limits).

## Evidence (aggregate counts; 25 stages, the original window as the oracle, identity-based)
Stages: levels/substages 0-0, 0-1, 0-3, 1-0, 1-1, 1-2, 2-0, 2-1, 2-2, 3-0, 3-1, 3-2, 3-3, 3-4, 3-5, 3-7, 3-8, 4-0, 4-1 (scrolling) and 0-2, 0-5, 1-3, 2-3, 4-2, 4-3 (camera stays within 200 px: boss-arena-like). Movement per run: right, stop, left, stop, right, down, right, up, left, right, stop, left, stop, right (repeated direction changes, vertical movement, returns through loaded sections).
* Original layout objects not created by this variant: **0 of 234** (comparison restricted to the part of each run before the original's first death/restart, which has different progression). A first attempt that moved the left deletion offset through the sprite-coordinate constant broke the game (159 of 230 missing); the final left deletion is a separate hook.
* Allocation failures: 7 entries in 2 sections, in one stage (4-0); both sections queued and recovered within 2 invocations; 0 expired, 0 dropped, 0 invalidated. Level resets: 39 (level starts and death/restarts), none with a pending entry in these runs.
* Objects created by the column loader that were already inside the visible picture at creation (sprite half-extent 16 px; 0 to 32 px range in the PR): right scroll 68% originally -> 12%; left scroll 87% -> 12%. Sprite level (observed pieces, real per-object extents): right scroll, first sprite already visible 68% -> 12%. Left scroll first sprites cannot be moved earlier: the original sprite builder constructs no piece for an object that far outside its own range, so only 3-8 left-scroll first sprites were observed and all were already visible.
* Cost: +0.04% guest instructions per frame (median over whole runs), +0.30% at most; peak live layout objects 31 (original 23); allocated-but-never-visible objects 7% -> 52% of creations.
* Audio: 0 faults, 0 clipped samples, non-silent in all runs. Replay: quick-save and rewind taken while four retries were pending replay identically (stress build with pools shrunk to 6/3/6 slots; occupancy never above 4; expiry after exactly 24 streamer invocations; no write outside the extent).
* The injected code is executed, not only read: `tests/test_castle_activation_exec.py` assembles the shipped `retry.asm` and runs it natively on a synthetic image against stubs of the original loader (initialization, level reset with four slots occupied, enqueue, dedup, queue-full, no enqueue while retrying or with a bad key, success, failure and ageing, expiry, invalidation, left deletion boundary, register/stack preservation, memory bounds), and mutations of the code are caught.

## State, register and flag argument
* State: 48 bytes at `0xFFFC00..0xFFFC2F`. The original game never wrote `0xFFFC00..0xFFFC3F` in 25 stages or in a 60,000-frame run from boot (logos, title, attract demos, levels); lowest stack pointer 0xFFFEA0, about 620 bytes above the extent, identical in the original and in the hook builds. The streamer (and so every hook) does not run before the first level initialization in the boot run; the level initialization has a single call site, which this routine hooks to clear and arm the state first. Each hook also arms or refuses on a wrong key before first use.
* The queued section's list pointer is not stored: it is a function of the level layout and is rebuilt as the original does; the retried loader receives the same a1/a2 as the original (checked against the original loader's own registers).
* Registers/flags: the displaced MOVEM (d2,d5,d7,a2) is reproduced by four pushes in the original memory order; the frame hook preserves d0-d7/a0-a6 and sets a6 to `0xFFFFFA80` exactly as the original `LEA` did; the fail hook preserves d0/d1/a0 and leaves d6 as the original `DBF` does; the level-reset hook preserves every register. The condition codes are rewritten by the instruction at each original continuation before any use (the loader entry's MOVEQ, the streamer's `MOVE.W 4(A6),D0`, the entry loop's `LEA/DBF`).
* A retried section calls the original loader, which skips entries whose loaded flag is set and applies its own rules for filtered or retired entries; nothing is created that an original section reload would not have created.

## Limits (not measured or not achieved)
* **32:9 is not provided.** At a 0x380 window with this queue: 24 first-time allocation failures in 7 frames (two thirds in the initial-fill burst of a level start or respawn), 335 repeated failures inside retries, 4 queue-full drops, 3 expiries; an intermediate 0x340 window still lost 3 original objects (stage 4-0). The live-object census at the failure moments shows ~30% speculative layout objects beyond the visible edge, ~36% visible layout objects and ~34% non-layout objects; essential demand alone (visible layout + all non-layout) reaches 33-39 at the 99th percentile and maximum against 32 slots per pool. Bookkeeping or prioritization cannot make that reliable without capacity or suppressing non-essential objects.
* Item collection, damage, collision and RNG behavior were not compared beyond identity of the created objects (frame-by-frame replay of an original script does not stay bit-identical because extra per-frame work shifts timing); no duplicated live activation can occur because the original loader's loaded flag guards every creation.
* The launcher flow (approval, installation, build, selection, save isolation) was run on the real image by driving the launcher library; see the PR.
