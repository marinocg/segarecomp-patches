# Castle of Illusion: debug free-fly (GAMEPLAY-CHANGING while active)

A user-invoked **debug mode in the spirit of Sonic's debug mode**: Mickey floats freely through the level, ignoring floors, walls, ceilings, enemies and pits, so a level can be explored. A separate opt-in package (native ABI 2, no ROM edit, no guest code), independent of the activation variants; the presentation-only package `castle-of-illusion` is untouched. **It is an exploration aid: traversal with it is not evidence of normal gameplay correctness.**

## Controls (player 1)
* **A + B + C together** toggles the mode (an edge: holding does not toggle again). **The chord is taken away from the game completely, on entering and on leaving, until all three buttons are up** (no jump or throw on the toggling frame). Entering starts from Mickey's current position; leaving hands him back where he is (the game's gravity and collision apply again from there).
* While flying: the **d-pad** moves Mickey **3 px per frame**, **A held doubles it**. The game sees only Start, so **Start still pauses and unpauses the game while flying**. Mickey is kept inside the visible part of the screen: the game's camera follows him at its own limited speed and he waits at the edge. The camera is never written (the game streams the level column by column as it scrolls).
* Power is topped up while flying (the power word, the five HUD slot words and the HUD-upload flag, as Practice+ does). **Invulnerability is not claimed** (see Evidence).

## Safety: it acts only on a verified state
It can be switched on, and it writes, only while **a scrolling level runs** (plane A's scroll record is the one of a running level), **Mickey's slot is live** and **his power is 1..5**. It ends by itself, **without writing**, as soon as any of that stops being true, the **level changes** (0xFF44/0xFF46), or Mickey's own position is no longer the one the mode last wrote (a respawn or restart moved him by more than a collision correction, 48 px). So a stale coordinate is never written into a new level, a menu, a cutscene or a respawn, and a chord pressed in an unverified state is left to the game. The mode state (on/off, tracked position, level, chord state) is part of the save state (24 bytes; the earlier 16-byte format is refused); a state restored into another level ends the mode at its first verification.

## How it works (facts about the work RAM of this one image)
Mickey is the object slot at `0xDC00`: `+0x10` x and `+0x14` y (pixels, each followed by a fraction word), vertical velocity at `+0x1A/+0x1C` (16.16). Per frame the provider moves its tracked position before the game's frame logic (`post-input`), zeroes the velocity, and writes the position again at the frame's end (`frame-end`) so a collision correction cannot move him. Declared memory: the Mickey slot, the power/HUD words (read-write); plane A's scroll record `0xFA80..0xFA93` and the level words `0xFF44..0xFF47` (read only).

## Evidence
* **Real image** (private; viewer, scripted input, dummy video):
  * On level 1 Mickey walks into the ledge that stops him (control: x=1303, power 1). With the package, after the chord, he flies through the ledge and the rock face behind it, high above the level and across it; the camera follows; at the level's exit the game moves on to the next level.
  * **After the level change the mod wrote nothing further**: a run that idled 1,200 polls past the transition has exactly the same committed-write count (13,930) as a run stopped right after the flight, so no stale coordinate reached the next level. A fresh chord in the next level starts from that level's Mickey and flies normally (x 1921, camera 1726).
  * **Pause while flying**: Start pauses (the `PAUSE` text, frozen frame) and unpauses; the flight carries on. A d-pad movement while the game is paused only changes the tracked position (the game's logic is not running); no pause flag is relied on (the byte that toggled with Start in a headless test, 0xF400, also changes during ordinary play in the viewer, so a first version that trusted it never moved Mickey and was removed).
  * **Power**: on stage 4-0, flying low across the level (Mickey x from the start to 1999), power read 5 at all four sampled points (poll 3400, 3800, 4400, 5200), whereas the unmodified game on the same input stays at x=615 with power 2. **How many enemy contacts occurred during that traverse was not measured, so invulnerability is not demonstrated**; instant-kill hazards, bosses and cutscenes were not exercised.
* **Approval, installation and build** (product CLI): an install without approval is recorded as not approved; an approval naming another identity is refused (`E_APPROVAL_MISMATCH`); approving the exact identity installs it; the variant's effective image equals the original (no ROM edit); a viewer builds from the installed package and runs without a fault. The launcher GUI itself was not run.
* **Tests** (`tests/test_castle_debug_fly.py`, 19, mock ABI 2 host with declared ranges enforced; CI requires them): edge toggle and start position; 3/6 px steps in eight directions; velocity and fraction cleared; the frame-end re-assert after a simulated collision correction; screen margins and the signed vertical scroll; the camera never written; refusal when the record, Mickey's slot or power is invalid; **automatic end without any write or pad override** on a level change, a zeroed record, a freed slot, death, and a respawn (horizontal and vertical); a new level never gets the old coordinates; Start passes through; the toggling chord never reaches the game on either edge nor while held or partly held; restore at a frame boundary, mid-frame (no stale pad) and into another level; corrupt and old-format state refused; only declared ranges written. Mutation checks caught: the screen margin, the velocity clear, the frame-end re-assert, the level check in the validity test and at the frame's end, the chord consumption, the activation gate.

## Limits
* Flying above the top of a level's map shows blank tiles. Vertical-scroll levels were exercised only through the signed-scroll arithmetic test. One level (and the first screens of 4-0) were flown on the real image.
* Death, restart, menus and cutscenes are handled by the verification rules and covered by the mock tests; they were not triggered on the real image (the mode keeps power up, so a real death was not produced).
* Boss arenas, cutscene triggers and level exits do whatever the game does while flying (the first level's exit worked).
* Validated against product `marinocg/segarecomp` main `8d419ab` for the image `Castle of Illusion (USA, Europe)` `2d535ff7...c47c4f` only.
