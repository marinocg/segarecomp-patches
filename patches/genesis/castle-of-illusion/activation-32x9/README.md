# Castle of Illusion: object activation with deferral for 32:9 (GAMEPLAY-CHANGING)

An opt-in variant, separate from the presentation-only package [`castle-of-illusion`](../widescreen-practice/README.md), which stays available as the **unmodified-gameplay** alternative (its effective image is the original image) and is never modified by this one. It shares that package's provider byte for byte and, with the 16:9 and 21:9 variants, ONE generated guest routine (`scripts/gen_castle_retry.py`); the aspects differ only in the section lookaheads (right 0x2c0 / left 0x180 here). It **changes which layout objects exist and when**: explicitly gameplay-changing. The original object pools, initialization routines and game logic are used as they are; no pool is enlarged, no object is evicted or suppressed.

## The activation policy (final)
* **Nine typed ROM edits** (`edits/activation.edits`, every site asserts its original value): right lookahead 0x180 -> 0x2c0, left 0x71 -> 0x180, initial-fill bound 0x280 -> 0x4c0, row-loader span 4 -> 6, and five six-byte hooks (entry hook at 0x60c80, fail hook 0x60d40, frame hook 0x60f00, level reset 0x61200, left cull 0x61260; the deferral helper at 0x61300).
* **Deferral.** A section is *speculative* when its column lies beyond the ORIGINAL window (right of `(camera+0x180)>>7`, left of `(camera-0xF1)>>7`). It is deferred (queued; the hook returns as the loader would after loading nothing) when the layout pool (0xD400..0xDBFF) holds >= 20 objects AND fewer than **12** of the 16 ring slots are in use. The decision reads only the guest camera word and the pool. A deferred section keeps its age while it waits, is revisited once per streamer invocation, loads when the pool has room, and is dropped when it leaves the retry window (the original would not have loaded it; its streamer asks again on re-entry). In-window sections are never deferred.
* **Queue reservation (complete).** Speculative work takes a ring slot ONLY while fewer than 12 are in use, **on both paths**: a deferral (entry hook) and a speculative section that was loaded normally past the cap but failed to allocate (fail hook, same classification and cap; otherwise it is counted in `specdrop` and not queued, exactly as the original would never have loaded it). The last 4 slots are therefore only ever taken by original-window failures. *The previous revision applied the cap only to deferrals: a speculative section loaded past the cap that then failed took a reserved slot (reproduced by a chained test, fixed here).* No second queue, no scheduler.
* **No eviction.** Freeing a live object (0x1c94) was not implemented: no object class with an established lifecycle and reactivation semantics was identified.

## Evidence
**Executable fixture** (`tests/test_castle_activation_exec.py`; the product assembles the shipped code and it runs natively on a synthetic image; 3 variants x 44 scenarios): exact stop path, every register, SP, the CCR where it is live, the full RAM image outside the documented extent; deferral threshold/edges/camera dependence; the caller-visible CCR after its `ADDI.W #$80` identical deferred or loaded; mutation checks (threshold, cap, ageing, stamp, and the fail-hook cap: both new tests detect its removal). **Saturated lifecycle** (persistent queue state chained across real executions with evolving pool, camera and a failing loader): 12 speculative sections fill the cap, 8 more are loaded, fail and are dropped (`specdrop`), 4 original-window failures are queued in the reserved slots, more speculative demand changes nothing, sustained pressure ages only the essential ones, camera movement invalidates and counts, and freeing the pool loads every pending essential section in one invocation with 0 expirations; plus a seeded 70-step random run asserting every step that a speculative section never raises the ring above the cap and an essential failure is never lost while a slot is free. A fixture stub bug found on the way (success branch skipped 6 instead of 8 bytes; the stub did not reproduce the real loader's `a3` at scan exhaustion) is fixed.

**RAM ownership and stack.** The retry state is 0xFFFC00..0xFFFC8F (key, flags, 16 x 8-byte slots) and the diagnostics 0xFFFCA0..0xFFFCB5 (words): 0xB6 bytes. Static: every absolute address in the asm lies inside; a linear decode of the image found no absolute-address operand in 0xFFFC00..0xFFFCFF (only fixed-point immediates). **Measured on 44 real runs per build (176 runs, 29 stages, two routes): the original never writes any byte of 0xFFFC00..0xFFFCFF (0 frames with a nonzero byte); the variants write only inside the 0xB6-byte extent (0 frames with a nonzero byte outside it).** The deepest stack seen was 98 bytes below the reset SP 0xFFFF00 for the original and 150 bytes for the 32:9 code (200-dispatch sampling; 86 bytes at single-dispatch sampling), far above the 0x300-byte gap. Cold start and counters: a **cold start is "the key is not valid", whichever hook runs first**; the level-reset hook may run before the first streamer invocation, so it performs the cold clear itself (the previous revision armed the key there and the diagnostics kept their power-on garbage). The cold clear writes **exactly the declared 0xB6-byte extent** (45 longs + 1 word; the previous 46-long loop also wrote 2 bytes past it). A level reset with a valid key clears only the ring (0x90 bytes), so the diagnostics accumulate across levels. Tested with nonzero guard bytes on both sides of the extent in every seeded RAM image, the real sequences (reset first, then the streamer; streamer first), and the last diagnostic word; mutations (the old overshoot, a reset without the key check) are caught.

**Injected-code equivalence.** The original loader has two callers (0x6d5ac, 0x6d604); both continue with `ADDI.W #$80`, which rewrites X,N,Z,V,C, and neither reads d3, d6 or a3 afterwards (d4 is live and never touched): the CCR and those registers are dead at the loader entry and at a deferral's early return. The deferral decision and the entry/fail counters are nevertheless X-neutral (LEA/MOVEA/MOVE/ROR/ANDI/CMP/TST/ROL), the fail hook reproduces the exact CCR. The frame hook runs extra original-loader calls and cannot preserve X (no ADDX in the product assembler): X is dead there on every measured path (forcing X to 0 versus 1 gave a bit-identical machine digest over 3,002 frames), **not proven**.

**Visible consequences of deferral (lifecycle of every queued section, 29 stages, right/left route).** For each queued section the ring dump gives enqueue, whether it ever aged (genuine allocation failure) or only waited (intentional), entry into the original window, entry into the aspect's viewport and the allocation:

Reading: no speculative wait ever delayed an original-window object (all speculative loads precede the window); the only late original-window loads are 2 genuine failures per aspect, recovered in 4 frames. The cost of the deferral is confined to the margin outside the original window: at 21:9/32:9 many margin sections enter the (wider) viewport before they are loaded (up to ~20 s under sustained pool pressure) or leave it never loaded: objects there appear late or not at all while the pool is crowded, by design. The three genuine-failure sections that were invalidated were enqueued outside the original window and never entered it.

**What the 21 never-loaded margin sections contain, and what was visibly missing (Task B, measured from the game's own data).** The 21 sections (4 at 21:9 and 17 at 32:9, all from the initial fill of stages 4-0 and 2-0, waiting until a death or reset 300-1,000 frames later) were decoded from real RAM snapshots with the loader's own table walk (width byte at 0xCA02, section ids from 0xCA04, entries of one flags byte and eight data bytes, skipping entries whose flag bit for the current difficulty is set) and every object type was classified with the object-draw routine's own rule (an object draws pieces when its current animation frame's piece count is non-negative; every type seen live, 14 of them, draws):
* **13 of the 21 are empty sections** (no object at all); **8 contain 23 objects**, all of the drawable types `c2` and `65` (plus single entries of `50`, `0d`, `44`, `3f`): no non-visual trigger or spawner entry was identified among them (an entry of an unseen type, `44` and `3f`, cannot be classified).
* Of the 23 objects, **10 were inside the aspect's viewport while their section was unloaded, for 41 to 262 frames (median 105; 0.7-4.4 s)**; **none was ever inside the original window**; the others were outside the viewport for the whole wait.
* The deferral **queues empty sections too** (it decides before the loader looks at the section), so empty sections used ring slots (the ring peaked at its cap of 12); this did not cause an omission here (a section past the cap is loaded normally) but is wasted queue room. No change was made: the evidence does not establish a concrete problem.
* **Status: a measured limitation, not a visual acceptance result.** Ten drawable-type objects were inside the aspect's viewport while their section was unloaded (data-derived, no pixel observed). After human recordings exist (see the input recorder README), empty-section deferral avoidance and prioritising sections approaching the viewport are to be investigated **only if the visual evidence justifies a change**; until then the policy is unchanged.
* **Not confirmed visually.** The viewer pairs (shipped 32:9 versus a no-deferral reference) were identical until guest divergence and then differed by ordinary timing (same enemy and platforms, shifted by a frame); the viewer's input is keyed by host poll, not guest frame, so no controlled pair existed at the frames where the decode says objects were missing. The omission is therefore measured from game data, not from pixels. (A fix, if wanted, would be to skip empty sections before deferring and to lower the threshold for sections inside the viewport; neither was implemented.)

## Restore investigation (closed)
Guest state restores bit-identically (canonical machine digest at every frame boundary, boundary and mid-frame barriers, all variants). On stage 4-0 with constant input in the real viewer (21:9 and 32:9): from the second real frame after a quick-load every presented frame is bit-identical to the uninterrupted run; only the synthetic presentation frame and the first real frame differ, in the margins. The earlier 1 px observation was capture/input alignment (the viewer's pad script is keyed by host poll, not guest frame). The one-frame margin fallback is intentional fail-closed behaviour: the host accepts the provider's work-RAM snapshot only if its stamp is exactly one frame older than the frame being produced (`compat_ram_stamp + 1 == virtual_frame_count`) and a restore rewinds the counter. No runtime fix, no product PR.

Over 29 stages at 32:9 with an aspect-switch script: max 36 submitted commands/frame (host limit 64), max 61 candidates (scratch 128), exact selection removed up to 31 in one frame, 0 visible-command losses. Remaining `virtual_sprite_unpresented` refusals (0.15% of frames, identical across packages and aspects): composed sets with side pixels only under the COMFORT side treatment (ADR 0307). **Native-picture protection** (same guest, provider on versus actors-off, final packages at 16:9/21:9/32:9, red-water stages 3-5 to 3-7 = scene `a16x64-b16` confirmed from RAM, plus stages 4-0, 3-2, 1-1): 0 differing pixels inside the native picture in 720 sampled frames. **Not shown:** in none of those sampled frames did a submitted actor change a pixel in the margins, so actor continuity, animation, both-direction scrolling continuity, red-water occlusion and hardware-piece handover were **not demonstrated on the real image in this round** (they remain covered by the provider's unit tests; the previous round's real-image measurement is not re-run).

## Acceptance status (what was and was not done)
* **Done:** all of the above; 87 of 87 real-viewer smoke runs of the previous identities and a re-run of replay/quick-save/rewind there; CI green on the previous head (build, exec incl. provider tests with skips forbidden, repository, samples, visual).
* **Not done (stated honestly):** item collection, damage by cause, collisions/platforms, non-visual triggers, RNG effects, repeated-reward checks, boss fights and natural stage transitions. The scripted routes (right/left with jumps, walking) mostly end in game-overs and collect almost nothing (3 of 29 stages produced a score event); an automatic input-search bot built on snapshot lookahead did not produce a verified route (it could not tell the candidate inputs apart on a flat camera signal) and was abandoned: **no gameplay-completion claim is made.** The launcher GUI workflow was not run (no display session with the commercial image here); product-CLI install, approval, variant selection and viewer build succeeded for all four identities (previous round).
