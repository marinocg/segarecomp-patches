# Catalog format

`catalog/index.json` is the static, machine-readable index of every published package. It is **generated** from the `release.json` files (`scripts/build_catalog.py`) and contains no hand-edited data. Two JSON Schemas are the contract:

| File | Describes |
|---|---|
| [`catalog/schema/release-1.schema.json`](../catalog/schema/release-1.schema.json) | `patches/<platform>/<game>/release.json` (`release_format` 1): the per-release metadata of one game |
| [`catalog/schema/catalog-1.schema.json`](../catalog/schema/catalog-1.schema.json) | `catalog/index.json` (`catalog_format` 1): one flat entry per package |

`python3 scripts/validate_catalog.py` checks both schemas plus the rules a schema cannot express, using only the standard library. It implements exactly the schema keywords the two files use (`SUPPORTED`); a schema using any other keyword is itself an error, so a schema cannot silently weaken a check. Examples: [`catalog/examples/valid-catalog.json`](../catalog/examples/valid-catalog.json) (synthetic, describes no commercial image); the rejection fixtures are in `tests/test_validate_catalog.py`.

## Public URLs

The Pages build serves the authoritative files unchanged (the same validated input the catalog pages are generated from; a malformed catalog fails the build):

| URL | Content |
|---|---|
| `https://marinocg.github.io/segarecomp-patches/catalog/index.json` | the catalog (`catalog_format` 1), `application/json` |
| `https://marinocg.github.io/segarecomp-patches/schema/catalog-1.schema.json` | catalog schema (its `$id`) |
| `https://marinocg.github.io/segarecomp-patches/schema/release-1.schema.json` | `release.json` schema (its `$id`) |

They are static files with stable names: a new `catalog_format` adds `catalog-2.schema.json` and keeps the old URLs. `catalog/index.json` lists **published** packages only; a prepared release is not in it (see [releases.md](releases.md)). Generated by `site/src/pages/catalog/index.json.ts` and `site/src/pages/schema/[name].json.ts`; `site/scripts/catalog-test.mjs` checks byte equality and the `$id` URLs.

## Fields of a catalog entry

| Group | Fields |
|---|---|
| Identity | `id` (slug), `version` (SemVer), `name`, `release` (collection tag `vX.Y.Z`) |
| Target | `platform`, `game`, `game_path`, `revision`, `region`, `source_identity_kind` (`cartridge-image-sha256` or `disc-image-identity`), `bios_requirement` (`none`, `required`, `optional`), `source_image_sha256`, `patched_image_sha256` |
| Package | `package_sha256`, `package_size`, `package_identity` (manifest digest), `schema_version` (1 or 2), `native_abi`, `capabilities`, `bps_sha256`, `native_source_sha256`, `executable_code` |
| Trust and evidence | `trust` (`data-only`, `trusted-native-source`), `evidence_tier` (`synthetic-only`, `maintainer-attested`, `automated`), `license`, `gameplay`, `supported_scope`, `limitations` |
| Provenance | `source_revision` (`repository` URL, exact `commit` SHA-1, optional `tag` and `tag_commit`), `build` (`writer`, `writer_ref` pin, `deterministic`) |
| Distribution | `asset` (`name`, HTTPS `url`) |
| Supersession | `superseded_by` (`<id>@<version>`), optional |

Master System, Game Gear and Sega CD entries are first-class through `platform`, `source_identity_kind` and `bios_requirement`; no field assumes a cartridge.

## Rules the validator enforces

* **Digests are mandatory and well-formed.** A missing or non-SHA-256 digest is rejected.
* **HTTPS only, and pinned.** `asset.url` must be exactly `<source repository>/releases/download/<release>/<id>.segapatch`. A `latest` URL, a branch URL or `http://` is rejected.
* **Closed vocabulary.** An unknown trust class, evidence tier, platform or identity kind is rejected, as is any unknown field.
* **Consistency.** `trust`, `schema_version` and `executable_code` must agree; a native package needs `native_abi` and `native_source_sha256`; a native package needs an MIT or MPL-2.0 licence.
* **Immutability.** A published `(id, version)` never changes. `validate_catalog.py --baseline-ref <ref>` compares the catalog with the one at the base commit (CI passes the pull request's base): removing an entry, removing a field, or changing any existing field of one is rejected. Evolution is purely additive: new entries, new optional fields introduced by a compatible format revision (the `v0.1.0` entries gained `source_revision` and `build` this way, without touching an existing value), and a `superseded_by` pointer, which once set is itself immutable. A fix is a new version.
* **Supersession is additive and acyclic.** `superseded_by` must name an existing entry (a higher version when it is the same id), never itself, never in a cycle. A superseded version stays published and unchanged.
* **Provenance is verifiable.** `scripts/verify_provenance.py` (needs full history) checks that `source_revision.commit` exists and is an ancestor of the checkout, that the recorded tag still resolves to `tag_commit` and has the same tree, and that the manifest, BPS and provider source at that commit have exactly the digests in `release.json`.

## Schema version policy

* `catalog_format` and `release_format` are integers. **Additive** changes (a new optional field, a wider enum) keep the number; consumers must ignore fields they do not know only where this document says so. Today a consumer reading format 1 may rely on every field above.
* A change that removes or renames a field, changes a meaning, or tightens an existing field is a **new format number** with a new schema file (`catalog-2.schema.json`); format 1 stays valid, and the generator emits the old format until every consumer has moved.
* `.segapatch` `schema_version` and `native_abi` are independent of the catalog format (see [layout and versioning](layout-and-versioning.md)). Schema 3 / ABI 2 projects are unpublished sources and never appear in the catalog.
* The Pages build and the launcher read the same file. The site's reader (`site/src/lib/catalog.mjs`) additionally refuses malformed entries so a page can never show a missing digest.

## Consumption by the launcher

The product launcher (M10) needs, per entry: the package identity to match an installed package (`id`, `version`, `package_identity`); the download (`asset.url`, `package_size`, `package_sha256`) which it verifies before use; the applicability test (`source_identity_kind`, `source_image_sha256`, `bios_requirement`, `platform`); the trust decision (`trust`, `executable_code`, `native_abi`, `schema_version`); and the user-visible honesty fields (`evidence_tier`, `supported_scope`, `limitations`, `superseded_by`). Every one of these is a required field of format 1, and none requires a server: the catalog is a static file under HTTPS. Signatures are a separate, later task and are not part of format 1.
