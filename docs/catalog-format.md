# Catalog format

`catalog/index.json` is the static, machine-readable index of every published package. It is **generated** from the published release records and the package facts they select (`releases/<tag>.json`, `patches/<platform>/<game>/<patch>/package.json`; `scripts/build_catalog.py`) and contains no hand-edited data. The JSON Schemas are the contract:

| File | Describes |
|---|---|
| [`catalog/schema/catalog-2.schema.json`](../catalog/schema/catalog-2.schema.json) | `catalog/index.json` (`catalog_format` **2**): one flat entry per package, either a schema 1/2 patch entry or a schema 3 mod entry |
| [`catalog/schema/release-2.schema.json`](../catalog/schema/release-2.schema.json) | `releases/<tag>.json` (`release_format` 2): one collection release, its lifecycle and its explicit package allowlist |
| [`catalog/schema/package-1.schema.json`](../catalog/schema/package-1.schema.json) | a patch's `package.json` (`package_format` 1): the facts of each of its package versions |
| `catalog-1.schema.json`, `release-1.schema.json` | the first formats (`catalog_format` 1 and the per-game `release.json`), kept at their URLs for the documents published under them |

`python3 scripts/validate_catalog.py` checks the schemas plus the rules a schema cannot express (explicit selection, eligibility, uniqueness, immutability), using only the standard library. It implements exactly the schema keywords the files use (`SUPPORTED`, which includes `oneOf` and `const`); a schema using any other keyword is itself an error, so a schema cannot silently weaken a check. Examples: [`catalog/examples/valid-catalog.json`](../catalog/examples/valid-catalog.json) (format 2: two BPS packages and one schema 3 mod) and [`valid-catalog-1.json`](../catalog/examples/valid-catalog-1.json) (format 1), both synthetic and describing no commercial image; the rejection fixtures are in `tests/test_validate_catalog.py`.

## Public URLs

The Pages build serves the authoritative files unchanged (the same validated input the catalog pages are generated from; a malformed catalog fails the build):

| URL | Content |
|---|---|
| `https://marinocg.github.io/segarecomp-patches/catalog/index.json` | the catalog (`catalog_format` 2), `application/json` |
| `https://marinocg.github.io/segarecomp-patches/schema/<name>.schema.json` | `catalog-1`, `catalog-2`, `release-1`, `release-2`, `package-1` (each file's `$id`) |

They are static files with stable names: a new format adds a new schema file and keeps the old URLs. `catalog/index.json` lists **published** packages only; a prepared release is not in it (see [releases.md](releases.md)). Generated by `site/src/pages/catalog/index.json.ts` and `site/src/pages/schema/[name].json.ts`; `site/scripts/catalog-test.mjs` checks byte equality and the `$id` URLs.

## Fields of a catalog entry

Two entry shapes, told apart by `schema_version`. **Schema 1 and 2 entries are exactly the `catalog_format` 1 entries**: every field that existed keeps its name and meaning, and every value `v0.1.0`'s five entries were published with is unchanged (its four native ABI 1 entries later gained only the additive `abi_status`; a copy of `catalog-2.schema.json` from before that addition rejects the field).

| Group | Schema 1/2 patch entry | Schema 3 mod entry |
|---|---|---|
| Identity | `id` (slug), `version` (SemVer), `name`, `release` (collection tag `vX.Y.Z`) | the same |
| Target | `platform`, `game`, `game_path`, `revision`, `region`, `source_identity_kind`, `bios_requirement`, `source_image_sha256`, `patched_image_sha256` | `platform`, `game`, `game_path`, `source_path`, `source_identity_kind`, `bios_requirement`, **`images`** (`[{label, sha256}]`: the exact images it targets). No `revision`/`region` strings, no patched image, no single source image |
| Package | `package_sha256`, `package_size`, `package_identity` (manifest digest), `schema_version` (1 or 2), `native_abi` (1), `capabilities`, `bps_sha256`, `native_source_sha256`, `executable_code` | `package_sha256`, `package_size`, `package_identity`, `schema_version` (3), `native_abi` (2), `capabilities` (non-empty), `executable_code` (true). **No `bps_sha256`, `patched_image_sha256`, `source_image_sha256` or `native_source_sha256`**: a mod is not a BPS/ROM transformation, and no placeholder digest stands in for one |
| Trust and evidence | `trust` (`data-only`, `trusted-native-source`), `evidence_tier`, `license`, `gameplay`, `supported_scope`, `limitations` | `trust` (`trusted-native-source`), `evidence_tier`, `license` (MIT or MPL-2.0), `gameplay`, `supported_scope`, `limitations` |
| Provenance | `source_revision` (`repository`, exact `commit`, optional `tag`, `tag_commit`), `build` (`writer`, `writer_ref`, `deterministic`) | the same; `build.writer` is `segarecomp mod pack` and `writer_ref` the product revision that produced the archive |
| Distribution | `asset` (`name`, HTTPS `url`) | the same (the URL is derived from the release that lists the package) |
| Supersession | `superseded_by` (`<id>@<version>`), optional | the same |
| ABI deprecation | `abi_status` (`deprecated`), derived by the generator for every `native_abi` 1 entry ([retention policy](abi1-retention.md)) | none |

`game_path` is the game directory (`patches/<platform>/<game>`) and keeps its historical meaning for every published entry. `source_path` (the patch directory, `patches/<platform>/<game>/<patch>`) is present on entries from releases built in the per-patch layout; when it is absent the sources were under `game_path` at `source_revision.commit`. Master System, Game Gear and Sega CD entries are first-class through `platform`, `source_identity_kind` and `bios_requirement`; no field assumes a cartridge.

## Rules the validator enforces

* **Digests are mandatory and well-formed.** A missing or non-SHA-256 digest is rejected.
* **HTTPS only, and pinned.** `asset.url` must be exactly `<source repository>/releases/download/<release>/<id>.segapatch`. A `latest` URL, a branch URL or `http://` is rejected.
* **Closed vocabulary.** An unknown trust class, evidence tier, platform or identity kind is rejected, as is any unknown field.
* **Consistency.** `trust`, `schema_version` and `executable_code` must agree; a schema 2 package needs `native_abi` and `native_source_sha256` and an MIT or MPL-2.0 licence; a schema 3 package needs `native_abi` 2, capabilities and its `images`, and a fabricated BPS or ROM field is an unknown field and is rejected.
* **Explicit release membership.** A release lists exact `id@version` selections; every one must exist in a `package.json`, belong to an `eligible` patch ([releases.md](releases.md)) and be listed by no other release. A published release record cannot be removed, and the generated catalog cannot drop a published entry.
* **Immutability.** A published `(id, version)` never changes. `validate_catalog.py --baseline-ref <ref>` compares the catalog with the one at the base commit (CI passes the pull request's base): removing an entry, removing a field, or changing any existing field of one is rejected. Evolution is purely additive: new entries, new optional fields introduced by a compatible format revision (the `v0.1.0` entries gained `source_revision` and `build` this way, without touching an existing value), and a `superseded_by` pointer, which once set is itself immutable. A fix is a new version.
* **Supersession is additive and acyclic.** `superseded_by` must name an existing entry (a higher version when it is the same id), never itself, never in a cycle. A superseded version stays published and unchanged.
* **Provenance is verifiable.** `scripts/verify_provenance.py` (needs full history) checks that `source_revision.commit` exists and is an ancestor of the checkout, that the recorded tag still resolves to `tag_commit` and has the same tree, and that, in the layout that commit had (`source_layout`), the manifest, BPS and provider source of a schema 1/2 package have exactly the recorded digests and a schema 3 package's `mod.toml` names its id and version.

## Schema version policy

* `catalog_format`, `release_format` and `package_format` are integers. **Additive** changes (a new optional field, a wider enum) keep the number. A change that removes or renames a field, changes a meaning, or adds an entry shape an older reader cannot represent truthfully is a **new format number** with a new schema file.
* **`catalog_format` 2 is that case.** A schema 3 mod has no single source-image digest and its catalog entry records no BPS or patched-image digest (a mod that carries an optional `bps-image` payload keeps that delta and its `target_sha256` in `mod.toml`, which the package identity covers), so it cannot be a format 1 entry without fabricating those fields. Format 2 therefore adds the second entry shape and nothing else; a reader that only understands format 1 sees `catalog_format: 2` and must refuse the file instead of misreading a mod entry. A reader that understands format 2 reads every format 1 entry unchanged. The generator emits format 2.
* `.segapatch` `schema_version` and `native_abi` are independent of the catalog format (see [layout and versioning](layout-and-versioning.md)).
* The Pages build and the launcher read the same file. The site's reader (`site/src/lib/catalog.mjs`) accepts formats 1 and 2 and additionally refuses malformed entries so a page can never show a missing digest or a fictitious BPS field.

## Consumption by the launcher

The product launcher (M10) needs, per entry: the package identity to match an installed package (`id`, `version`, `package_identity`); the download (`asset.url`, `package_size`, `package_sha256`) which it verifies before use; the applicability test (`source_identity_kind`, `source_image_sha256`, `bios_requirement`, `platform`); the trust decision (`trust`, `executable_code`, `native_abi`, `schema_version`); and the user-visible honesty fields (`evidence_tier`, `supported_scope`, `limitations`, `superseded_by`). Every one of these is a required field of its entry shape (a schema 3 entry states its `images` instead of one source image), and none requires a server: the catalog is a static file under HTTPS. Signatures are a separate, later task and are not part of format 1.

For a schema 3 entry the launcher additionally needs `native_abi` (2), `capabilities` and `images` to decide compatibility, and a build of segarecomp that can install schema 3 packages (`segarecomp mod install`). **No tagged segarecomp release can install a schema 3 package yet** (the installer and its ADRs are on the product's main branch after v0.8.0), so the catalog advertises these entries for a future launcher and the site says so; do not claim end-user installation until a product build that does it has been tested.
